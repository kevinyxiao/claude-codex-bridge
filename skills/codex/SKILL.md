# /codex — use GPT (and extra Claude seats) from inside Claude Code

BRIDGE = `python3 "${CLAUDE_SKILL_DIR}/scripts/bridge.py"` (keep the quotes; the path may contain spaces). It runs the `codex` and `claude` CLIs that are already signed in on this machine, so it works on any Mac with any accounts. Each call is a job under `~/.cache/codex-claude-bridge/jobs/<id>/` (private to the user); only a bounded result comes back to you. Installed as a plugin this skill is `/claude-codex-bridge:codex`; in the personal skills layout it is `/codex`.

The read-only modes (`review`, `ask`, `council`, `fanout`, `status`, `monitor`, `result`, `merge`, `cancel`, and the bare `doctor`) are pre-approved by this skill. `task` and `reply` are not: they can write files, so the user sees and approves the exact command. `doctor --json` and `doctor --clear-lifecycle` are not pre-approved either (the clear changes the evidence file), so the user sees those too.

Arguments you received: `$ARGUMENTS`

## Seats

A seat is `model[|model…][:effort[|effort…]][@fast]`. Several seats, comma-separated, run in parallel, each in its own process with an empty context. The names after a `|` are the seat's preference list: the only models (or efforts) the seat may move to, and only once no account can run the first one.

- GPT via Codex: the families `astra`, `sol`, `terra`, `luna`. A family name always means the newest model in that family; the table `models.json` beside this skill says which, together with any newer GPT model this Mac's check adopted on its own (below), and `doctor` lists the exact IDs. A current model ID from the table means the same seat; a retired or superseded ID, an old alias of a generation or an unknown slug is refused in one line that names the replacement. Efforts `low|medium|high|xhigh|max|ultra`; `ultra` adds automatic delegation to Codex subagents and cost about 1.5× the tokens of `max` in the one measurement taken (a small diff). `luna` tops out at `max`. `@fast` selects Codex's Fast tier (quicker, more usage).
- Claude via a separate Claude Code process: the families `fable`, `opus`, `sonnet`, `haiku`, likewise the newest in each, and the pinned `opus-5` seat (Kevin's K1 seat: legal work stays on the pinned Opus). Efforts `low|medium|high|xhigh|max` (`haiku` takes none). These seats run under Claude Code's restricted profile: an explicit tool list, no MCP servers, no inherited settings, about 4,400 tokens of startup context, and automatic model switching off. Read-only seats have no shell at all.
- No silent descent. A Codex seat whose account rejects its model or effort at startup is tried on another account whose catalog can run it; it moves to another family or effort only when the seat spec lists one after a `|` (`astra|sol:ultra`, `astra:ultra|max`), and the answer then leads with a `NOTICE:` line naming the descent. Without a preference list the seat ends on the rejection, and the failure names the list that would have allowed it (the table's `fallback` edges are that suggestion, never applied on their own). Every other rejection ends the seat; a Claude seat is never moved to another model. The pinned `opus-5` seat is in the table and switched on (`k1_seat.enabled`): asked for as `opus-5`, it runs the pinned id for legal work; `opus` keeps meaning the newest Opus, and the pinned id typed bare is still refused as superseded (ask for `opus-5`).
- Every seat is checked before it launches: the name, a lifecycle marker left by the last models check, the effort, and the CLI's version against the model's floor in the table (for example Codex CLI 0.156.1 for `luna`, 0.153.0 for `astra`, `sol` and `terra`, and for a GPT model adopted automatically the Codex that listed it; Claude Code 2.1.280 for `opus`, 2.1.257 for `fable`, 2.1.284 for `sonnet`, 2.1.295 for `haiku`; `doctor` prints the full list). The check runs again right before the seat's first launch, after any wait for an account. A refusal is one line naming the fix: for Codex the upgrade of the installation it found (`npm install -g @openai/codex@latest`, `brew upgrade codex`, updating the ChatGPT app, or OpenAI's installer) or `CODEX_BIN`; for Claude Code `claude update`. Relay it as it is and never substitute another model yourself.
- The same model twice at different efforts is fine: `astra:max,astra:ultra`. `--effort E` applies to every seat that does not name one, and replaces the efforts built into the default seat lists.
- Defaults when no `--seats` is given: single seat `astra:ultra`; `review` and `council` use `astra:ultra,sol:ultra,opus:max`. The environment variables `BRIDGE_DEFAULT_SEAT`, `BRIDGE_REVIEW_SEATS`, `BRIDGE_COUNCIL_SEATS` override those defaults on a machine; `doctor` prints the effective values. Change seats only when the user asks.
- `task` takes exactly one seat. For several delegated tasks make separate calls, and never run two write tasks against the same working tree at once.

Seats run on relay-routed accounts automatically: when the `/relay` skill is installed and has accounts for a seat's vendor, the seat asks relay which account to spend now and runs under it, and the footer, `status` and `monitor` show `account=<label>`. A seat that hits a usage limit reports it to relay and moves to the next account: a Codex seat is restarted with its original prompt (a `--write` Codex seat that had already begun work fails explicitly instead, naming the account and thread, so no side effect is repeated), a Claude seat is continued in its own session on the next account. When relay has no account to offer, the seat waits in state `waiting` until the time relay names, showing relay's reason for each account (an account can be out until its reset, or held back because relay has not been able to read its usage for an hour, in which case relay is asked again every minute); all of a seat's waits together end `BRIDGE_ROUTED_MAX_WAIT` seconds after its start, default 7200, or at its own `--timeout` when that is sooner. A seat that cannot wait that long fails with relay's reasons, the time relay said to ask again, and which account holds its half-run thread. `reply` runs on the seat's recorded account; a Codex reply first re-checks that account's live sign-in through relay and refuses if it changed or cannot be verified, so a follow-up never spends a different account than the one that holds the thread. `BRIDGE_ROUTER=off` turns this off (seats then use the machine's own logins and the usage-limit ladder below), and wrapping the engine in `relay exec -- bridge.py …` is no longer needed for any of it.

With the model registry installed (the `model-registry` skill; `doctor` names the copy it found), a Codex seat is routed only to the accounts whose fresh catalog lists its model at the requested effort: the bridge reads each account's catalog through the app-server under that account's own home when its stored snapshot is stale or was taken under another launch configuration, confines relay's choice to that capable set, re-checks the picked account right before the launch, and re-picks within the rest of the set after a startup rejection. When relay cannot apply the set (an older relay, no Codex accounts) or is not installed, the bridge validates this machine's own login the same way and launches there only when its catalog lists the model; it never falls through to an unchecked login. Every attempt records what was requested, what the table expected and what the vendor reported (a Codex seat from its own window of the rollout file under the account's home, a Claude seat from its own stream) in `provenance-<seat>.jsonl` and in `findings-<seat>.json` (`_model_requested`, `_model_expected`, `_observed_models`, `_downgraded_from`, `_substitution`); a model the seat did not ask for is a substitution, noticed and marked `SUBSTITUTED` in the footer, and `--strict-model` (every model-starting mode and `reply`) fails such an attempt, as it fails one whose observation could not be collected; without a registry the flag is refused up front rather than silently unmet.

## 1. Decide the mode

First word = mode. If none: a question → `ask`; "review", "audit", "check my changes" → `review`; "do", "implement", "fix" plus a task → `task`; "compare", "what do the models think" → `council`. Pass every other flag through to BRIDGE unchanged, except `--wait`, which is for you.

## 2. Foreground or background

Ultra and max seats take minutes; a review of a real change can take ten or more.

- In a persistent interactive session where you will still be here when it finishes: run long modes with `Bash(..., run_in_background: true, description: "multi-model review")`, tell the user it is running and that `/codex monitor` shows live progress, and relay the output verbatim when the completion notification arrives.
- In a non-interactive run (`claude -p`), inside a subagent, when the user passed `--wait`, or whenever you are not sure the session will outlive the job: never use `run_in_background`. Run in the foreground with `--timeout 540` passed to BRIDGE and `timeout: 600000` on the Bash call; the engine then ends the job inside that window (killing any seat still running) and returns whatever was produced, with exit status 3 for a partial result. Relay that output and its status; a job you launched must reach a terminal state and be relayed before your turn ends. If a Bash call nevertheless returns a background task id, wait for its completion notification, then run `result <job>` and relay the output before ending.
- `status`, `monitor --once`, `result`, `cancel`, `doctor` are quick; run them in the foreground. `reply` runs a model turn: run it in the foreground with `--timeout 240` (longer only if the user asks) and relay the answer.

## 3. review

1. Write INTENT: two to four sentences, in your own words, on what was changed and why, from this conversation. Do not paste the diff; the engine freezes it into `review.patch` and every seat reads that same file.
2. From the project directory (BRIDGE resolves the git root; or pass `--cwd`):
   ```bash
   python3 "${CLAUDE_SKILL_DIR}/scripts/bridge.py" review [--base <ref> | --commit <sha>] [--seats …] --intent "<INTENT>" [--focus "<focus>"]
   ```
   If INTENT or FOCUS contain quotes or several lines, keep them off the command line: pass `--intent-stdin` and feed a JSON object on stdin:
   ```bash
   python3 "${CLAUDE_SKILL_DIR}/scripts/bridge.py" review --intent-stdin <<'JSON'
   {"intent": "<INTENT>", "focus": "<focus>"}
   JSON
   ```
   Changes above 4,000 diff lines are refused: review per commit (`--commit`), against a nearer base, or slice with `fanout`; `--allow-large` overrides when the user accepts the thinner attention.
3. The output is the merged report: one row per issue with priority, location, which seats found it and consensus marks (two seats count as agreeing only when their titles agree and their proposed fixes agree; weaker matches stay separate rows marked "possibly the same as"), then each seat's assessment, then a footer with the job id, per-seat seconds, tokens, and thread ids. Exit status 3 means some seats failed, a seat returned no usable findings JSON, or the merge failed, and the report is partial; 1 means every seat failed. Relay the report verbatim, including any note about the change or the working tree having moved during the review.
4. Then stop and recommend: which findings you would fix and why. Ask before editing files, unless the user already said to fix whatever the review finds; in that case fix, then run a fresh `/codex review`.

## 5. reply, status, monitor, result, cancel, doctor

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/bridge.py" reply <job|last> [--seat astra] -- "follow-up"   # continues that seat's own thread; its context, not yours
python3 "${CLAUDE_SKILL_DIR}/scripts/bridge.py" status [job]         # jobs (each with its notice count, first notice and any `requested -> ran` fallback); with a job: its NOTICE lines, then per-seat state, elapsed, context (Claude seats: exact tokens and % of window; Codex seats: per-turn totals only), tokens, turns, steps, last activity
python3 "${CLAUDE_SKILL_DIR}/scripts/bridge.py" monitor <job> --once  # the same table, one snapshot
python3 "${CLAUDE_SKILL_DIR}/scripts/bridge.py" result <job> | cancel <job> | doctor
```

- A seat in state `waiting` is parked for one of the causes below; its activity line names the cause in plain words and says when it retries, and `status`/`monitor` show it. A seat that had already started working resumes its own thread after the wait instead of starting over. `cancel` interrupts every wait.
  - `usage limit hit (n)`: the usage-limit ladder of an unrouted seat (three attempts about twenty seconds apart, then about an hour, repeating; every step is jittered ×0.6–1.4 so seats never retry in lockstep).
  - `Codex throttled (<evidence>); throttle wait n` or `Codex unreachable (<evidence>); throttle wait n`: ChatGPT refused or was overloaded ("exceeded retry limit, last status: 429", "429 Too Many Requests", "503 Service Unavailable", "currently experiencing high demand", "Selected model is at capacity", "Flex capacity unavailable", `server_overloaded`) or the Codex CLI could not reach chatgpt.com (connection refused/reset, DNS failure, "stream disconnected before completion", "error sending request", "waiting for network"). This is **not** a usage limit: the seat does not tell relay, does not move to another account and does not enter the usage-limit ladder. An interactive seat waits about 60 s, then about 300 s, and then fails with `Codex throttled twice (<evidence>); not retried further` (reviews never wait on Codex: relay that line and let the user decide). A batch seat waits 300 s, 900 s, 1800 s and then every 1800 s (×0.8–1.2) for as long as it takes. The ladder is the one of the class the seat was admitted as (an interactive seat over the interactive budget waits like a batch seat here too). A throttled attempt that had already begun work resumes its thread, and from then on the seat is pinned to that account for every retry, busy refusals included, as a `reply` is (the thread lives in that account's home).
  - `waiting for Codex capacity: N live sessions of M allowed for <class> seats on <home>`, `held: computer-use task <dir> has priority`, `batch launches paused by <PAUSE path>`, `post-wake quiet period`, `launch pacer: …`, `network down: chatgpt.com unreachable`: the capacity gate (next section). The time a seat spends in a throttle wait, and the whole capacity-admission interval (the lock waits, probes and rollout scans of every re-check as well as the sleeps), is not charged to its `--timeout`; a routed seat's wait budget moves with it too (`BRIDGE_ROUTED_MAX_WAIT` stays its own limit). After every admission, held or not (a first decision can block on the account lock for a while and then admit directly), a pinned seat whose sign-in verification went stale (a hold, or a throttle wait before an immediate re-admission) verifies it again, and then the model check runs again right before the launch, so a deprecation or retirement marker published during the hold, the lock wait or the verification itself refuses it, as after a routing wait.
- `reply` to a waiting seat refuses in one line that names the cause; cancel the job or wait.
- Codex does not expose a seat's live context occupancy through its non-interactive interface; the table says so rather than guessing.
- `doctor` runs the free models check every time it is invoked (the local Codex catalog through the signed-in `codex`, npm's latest Codex, Anthropic's model-deprecations and model-overview pages; no model call, no relay); before a model-starting mode the bridge re-runs the same check automatically at most once a day (`policy.recheck_after_hours`). It prints its verdict (`OK`, `UNVERIFIED` when a source could not be read, `FAIL` when a current model is deprecated, retired, missing or superseded, or a CLI is below a floor), the table's current models and floors, the automatic promotions in force and the newer models it held back (with the reason), the resolved CLIs with their versions, and any sticky lifecycle marker; `--json` prints the object, `--clear-lifecycle <id> --reason "<why>"` clears a marker after review, `--undo-promotion <family> --reason "<why>"` reverses this Mac's latest automatic promotion of a GPT family and blocks that model here. Under the default gate a failed check leads every new job's output with a `NOTICE:` line; `BRIDGE_MODELS_GATE=refuse` (or `policy.stale_gate` in the table) refuses new jobs until doctor is clean.
- New GPT models are adopted without editing the table: when the check finds a newer GPT model of a family (a higher-numbered name of the family's form, listed as visible with every effort the current head offers, no preview or lifecycle status) in the catalog of this Mac's own signed-in Codex, that model becomes the family's head on this Mac (recorded in `models-evidence.promotions.json` beside the evidence file; `models.json` is never written). The old head is then refused as superseded. For a week a job that runs the new head leads with `NOTICE: models: <family> runs <id>, promoted automatically on <date> ...`: relay that line to the user. Nothing is demoted automatically, hidden, preview, codename and chat models are never adopted, and Claude families are not promoted automatically (a newer Claude model is a `stale` finding until the table is updated). `BRIDGE_MODELS_PROMOTE=off` stops new promotions.
- If `doctor` reports a missing or signed-out CLI, tell the user to run the plugin's `bootstrap.sh`, or `codex login` / `claude`. If it reports a CLI below a floor, relay the upgrade command it prints. Never ask for an API key and do not improvise another auth path.

## 5a. Capacity, throttling and the computer-use lease

On 2026-10-12 about 120 concurrent batch seats on one ChatGPT login (300–400 live Codex sessions with their subagents) made ChatGPT refuse (429s), broke Codex's Chrome plugin and starved three computer-use tasks; the bridge then misread the 429 as a usage limit and retried every seat in lockstep. Every Codex launch now passes a capacity gate before it starts, on the account (CODEX_HOME) it will really use; Claude seats are not gated.

- **Launch classes.** Every job is `interactive` or `batch`: `--class` on the subcommand, else `BRIDGE_CLASS`, else the default (`fanout` is batch; `ask`, `council`, `review`, `task` and `reply` are interactive). **Any driver script that launches many seats must set `BRIDGE_CLASS=batch`** (never call it "fleet": that word names other things here). An interactive seat is admitted while the account's live sessions plus its weight stay within the session cap; a batch seat only below the cap minus the interactive reserve, and only when no computer-use task holds the priority lease, no `PAUSE` file is set and the launch pacer allows. Interactive launches are self-limiting: at most `interactive_budget` of live interactive weight per account (an ultra seat weighs 3, any other 1); beyond that a seat is treated as batch for the whole of its handling (the admission, the network hold and the throttle ladder) and the job carries one notice (`interactive budget used; this seat waits like a batch seat`). A two-seat interactive review therefore never waits on the lease, the PAUSE file or the pacer's quiet period and rate; it does wait, for at most 120 s, when chatgpt.com does not answer a TCP probe, and at the hard cap it waits up to 900 s (`BRIDGE_CAPACITY_MAX_WAIT_INTERACTIVE`) and then fails with a line naming the counts. A batch hold is unbounded and cancellable and never ends in an error.
- **The numbers** (`~/Library/Application Support/legal-research/codex-capacity.json`, Kevin's file; `LR_CU_COORD_DIR` moves the dir): `session_cap` 100, `interactive_reserve` 16, `interactive_budget` 24, `cap_mode` `shadow`. Environment overrides: `BRIDGE_CODEX_SESSION_CAP`, `BRIDGE_CODEX_INTERACTIVE_RESERVE`, `BRIDGE_INTERACTIVE_BUDGET`, `BRIDGE_CAP_MODE`, `BRIDGE_CODEX_WEIGHT_ULTRA`. `cap_mode` governs only the two session-count limits: in `shadow` (the default) the bridge computes the decision, logs `would hold: …` once per seat (stderr and the events log) and admits; `enforce` holds. The lease, the PAUSE file, the pacer and the throttle class are always enforced. `BRIDGE_CAPACITY=off` (emergency only) turns the whole gate off; the throttle class and the jittered ladders still apply.
- **The priority lease.** A running computer-use task (`codex_task.py run`) holds a locked holder file in `<coord dir>/codex-cu-priority.d/`, and leaves a reservation there across its wait-retry cycles. While any holder is locked by a live runner, or a reservation for this Mac has not expired, batch seats hold (`held: computer-use task <dir> has priority`) and interactive seats are admitted with one notice per job. The bridge only reads these files (a shared-lock probe), never writes or prunes them; a holder file nobody locks is stale and does not hold.
- **The PAUSE file.** `touch ~/.cache/codex-claude-bridge/capacity/PAUSE` (`BRIDGE_CAPACITY_DIR` moves the dir) holds every batch launch on this Mac until it is removed; interactive seats are unaffected. This is the standard way to pause any bridge-launched batch.
- **The pacer** (per account, `<capacity dir>/<key>.pacer.json`). After a Mac wake (`kern.waketime` newer than last seen), the end of a network outage (the TCP probe to chatgpt.com:443, cached 10 s, re-probed every 30 s while down) or any seat ending in the throttle class, batch launches ramp: 4 per minute (`BRIDGE_RAMP_START`), doubling every 120 s (`BRIDGE_RAMP_STEP`) until the doubled rate reaches the cap per minute (then the ramp is over and cleared from the pacer; `BRIDGE_RAMP_START=0` or `BRIDGE_RAMP_STEP=0` disables the ramp), with ±30% jitter on every slot; the first 60 s after a wake admit no batch launch at all (`BRIDGE_WAKE_QUIET`). Outside a ramp, batch launches on one account are at least 1.5 s apart (`BRIDGE_MIN_GAP`, ±50%; 0 allowed). While the probe fails every class holds (interactive at most 120 s). Interactive seats skip the quiet period and the rate limit. Test overrides: `BRIDGE_NET_PROBE=host:port|off`, `BRIDGE_FAKE_WAKETIME`, `BRIDGE_THROTTLE_WAIT_SCALE`, `BRIDGE_HOLD_POLL` (the re-check interval of a held seat, default 20 s), `BRIDGE_NETWORK_HOLD_INTERACTIVE` (default 120 s).
- **Visibility.** Every change of a hold's cause prints one `[bridge] capacity: <seat>: <cause>` line on stderr (batch drivers capture it); each job gets one capacity notice; `<capacity dir>/events.jsonl` records admit, hold, release, stale-lease, shadow and trigger events with the counts. `doctor` and `status` end with the capacity section: per account its live sessions (top-level and subagents, counted from the rollout files under its CODEX_HOME; with the number of long turns, of files whose tail could not be read at all and of turns untouched for over two minutes, when there are any), pending admissions, the cap and reserve, the mode, the lease state with the holder's task dir, the PAUSE file and the ramp state.

## 6. Context discipline

- Relay BRIDGE output only; never open `events-*.jsonl`. For detail on one finding, `Read` the specific `last-<seat>.md` or `findings-<seat>.json` named in the footer.
- Follow-ups go to the seat's own thread with `reply`; your context stays small.
- One review job per change set; re-review after fixes with a fresh `/codex review`.
