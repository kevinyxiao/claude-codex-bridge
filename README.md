# claude-codex-bridge

Use both frontier coding agents from either one, on any machine, with whatever accounts that machine is signed into.

- **`/codex` (alias `/gpt`) inside Claude Code** calls OpenAI's models through the local `codex` CLI: the Astra, Sol, Terra and Luna families, always the newest model in each. It can also add extra Claude seats. (Installed as a plugin the commands are `/claude-codex-bridge:codex` and `/claude-codex-bridge:gpt`; in a personal skills layout they are `/codex` and `/gpt`.)
- **`$claude` inside Codex** calls Anthropic's models through the local `claude` CLI: the Fable, Opus, Sonnet and Haiku families, always the newest model in each.

Nothing in this plugin names an account, a key, or a machine. Each computer contributes its own `codex login` and its own Claude sign-in. Change accounts, change nothing here.

## Seats: any model, any effort, as many as you like

A seat is `model[:effort][@fast]`. Several seats, comma-separated, run **in parallel, each in its own process with an empty context**. Mix vendors freely.

| Vendor | Models | Efforts |
|---|---|---|
| Codex (OpenAI) | the families `astra`, `sol`, `terra`, `luna` (each the newest model in its family; `doctor` lists the exact IDs), or a current model ID from the table | `low` `medium` `high` `xhigh` `max` `ultra` (`luna` stops at `max`) |
| Claude Code (Anthropic) | the families `fable`, `opus`, `sonnet`, `haiku`, or a current model ID from the table | `low` `medium` `high` `xhigh` `max` (`haiku` takes none) |

`ultra` is Codex-only: maximum reasoning plus automatic delegation to Codex subagents. In the one measurement taken (a 20-line diff) it used about 1.5× the input tokens of `max` for the same findings; whether it finds more on large changes has not been measured. `@fast` selects Codex's Fast tier (quicker, more usage). `--effort E` applies to every seat that does not name its own. Examples: `astra:ultra,sol:ultra,opus:max` · `astra:max,astra:ultra` · `fable:xhigh,sonnet:high,luna:medium`.

## Model names: the newest in each family

- **A family name means the newest model in that family.** Which model that is today comes from one table, `skills/codex/models.json`, read by the engine on every call together with the GPT models this Mac's check adopted on its own (below; `doctor` prints both with the exact IDs and the versions they need); nothing else in the plugin names a model version. A current model ID from the table selects the same seat.
- **Retired and superseded names are refused, never mapped.** An old ID, an old alias of a generation or a name the table does not know is refused in one line that names the replacement (`refused seat '<old id>': <old id> is superseded by <head>. Use <family> (<head>).`). A `reply` to a seat that ran on a since-superseded model continues on the family's newest model and says so first.
- **No silent descent.** A Codex seat whose account rejects its model or effort at startup is tried on another account whose catalog can run it (with the model registry installed, the seat is routed only to such accounts in the first place, and never falls through to an unchecked login when relay cannot confine the choice). It moves to another family or effort only when the seat spec lists one after a `|` (`astra|sol:ultra`, `astra:ultra|max`), and only once no account can run the first choice; the answer then leads with a `NOTICE:` line naming the descent, the footer says `fell back from`, and `findings-<seat>.json` records `_downgraded_from`. Without a preference list the seat ends on the rejection and the failure names the list that would have allowed it (the table's `fallback` and `effort_fallback` edges are that suggestion, never applied on their own). A Claude seat is never moved to another model: it is launched with Claude Code's automatic model switching off, the model it actually ran is read from its stream, and a mismatch fails the seat and is reported. Every attempt's requested, expected and observed models are recorded (`provenance-<seat>.jsonl`; the merged review header lists each seat as requested -> ran), and `--strict-model` fails an attempt that ran another model or whose observation could not be collected (without the model registry, which collects the observation, the flag is refused up front).
- **The `opus-5` seat.** One pinned seat, `opus-5` (Kevin's K1 rule: legal work stays on the pinned Opus, the registry's `legal-opus-5` pin), is in the table and switched on (`k1_seat.enabled`): asked for as `opus-5`, it runs the pinned id for legal work, while `opus` keeps meaning the newest Opus and the pinned id typed bare is still refused as superseded (ask for `opus-5`). It is a bridge seat only: triad's relay workers are launched by alias, so `opus-5` is refused for them.
- **CLI floors.** Every model in the table names the CLI version it needs (`min_cli`): today Codex CLI 0.156.1 for Luna and 0.153.0 for Astra, Sol and Terra; Claude Code 2.1.280 for Opus, 2.1.257 for Fable, 2.1.284 for Sonnet, 2.1.295 for Haiku (below a Claude floor, that Claude Code still resolves the family name to an older model). A GPT model adopted automatically needs at least the Codex that listed it (its exact version, a prerelease included). A seat below its floor is refused before anything launches, and the refusal names the fix for the Codex that is installed: `npm install -g @openai/codex@latest` for an npm install, `brew upgrade codex` for Homebrew, updating the ChatGPT app for its bundled Codex, or OpenAI's installer (or point `CODEX_BIN` at a newer codex); for Claude Code, `claude update`. The bootstrap checks both CLIs (its `Codex version` and `Claude Code version` steps are `FAILED` below a floor, naming the same fix) and installs a current Codex with npm when none it finds meets the floor.
- **The free check.** `doctor` reads the local Codex catalog (through the signed-in `codex`, no model call), npm's latest Codex version (the registry's dist-tags endpoint), and Anthropic's model-deprecations and model-overview pages every time it runs, and keeps what it learned in `~/.cache/codex-claude-bridge/models-evidence.json`; before a model-starting mode the bridge re-reads the same sources automatically at most once a day (`policy.recheck_after_hours`). It says whether the table is current: `OK`; `UNVERIFIED` when a source could not be read; `FAIL` when a current model is deprecated or retired, missing from the catalog or superseded by a newer version, a CLI is below a floor, or the host overrides a model alias. A deprecation or retirement becomes a sticky marker that refuses the marked model until someone reviews it (`doctor --clear-lifecycle <id> --reason "<why>"`). Every new job composes the same verdict first: under the default gate (`warn`) a failed check is a leading `NOTICE:` line in the job's output; `BRIDGE_MODELS_GATE=refuse` (or `policy.stale_gate` in the table) refuses new jobs until `doctor` is clean. Doctor never consults relay, never runs a model, and prints no configuration values.
- **New GPT models are adopted automatically.** When the check reads this Mac's own Codex catalog and finds a newer GPT model of a family (a name of the family's form with a higher number, such as `gpt-<n>-terra`, listed as visible, no preview or lifecycle status, no sticky marker, every effort the current head offers), it makes that model the family's head on this Mac: the next seat named `terra` runs it, the old head is refused as superseded, and the model's floor is the Codex that listed it. The catalog counts only when a login stands behind it (the same app-server session confirms one; signed out, Codex lists its built-in models) and no catalog setting is changed. The step goes into `~/.cache/codex-claude-bridge/models-evidence.promotions.json`, never into `models.json` (which ships in the zip and lives in git); the check announces it on stderr, `doctor` lists every promotion and every model it held back with the reason, and for a week each job that runs the new head (directly or through a `|` preference list) leads with `NOTICE: models: <family> runs <id>, promoted automatically on <date> ...`. So a new model is in use within a day (the daily re-check before a model-starting command, or at once on `doctor`). It never goes the other way: nothing is demoted automatically, a lower or equal generation is never adopted, hidden, preview, codename and chat models (`gpt-daybreak-*`, `codex-auto-review`) never are, and a name the table refuses stays refused. `doctor --undo-promotion <family> --reason "<why>"` restores the previous head and blocks that model on this Mac (with promotion on, if the catalog lists another model newer than the restored head, the same check adopts it and says so; if that check cannot read the catalog, the next `doctor` tries again); a later `models.json` that names the model takes over from the ledger, and one that moves the head without naming it leaves this Mac on its newer model, which `doctor` says. Relay accounts whose catalog does not list the new head are left out of the seat's routing like any account that cannot run its model. Claude families are not promoted automatically (Anthropic's pages describe the API, not what this Claude Code can run): a newer Claude model stays a `stale` finding until the table is updated. `BRIDGE_MODELS_PROMOTE=off` (or `policy.auto_promote: false` in the table) stops new promotions; those already made stay until undone.
- **What is guaranteed, and where.** Seats the bridge launches (`/codex`, `$claude`, triad's critic) get the name rule, the floor, the marker check, the no-descent rule with its explicit preference lists, and the observed-model comparison. Triad's architect and tester are `/relay` workers, launched by relay as Claude Code processes on the family alias: before submission they get the same name rule (Codex models and the K1 seat refused), one effort for the whole list, and a preflight of the Claude CLI relay will run against the floors; after each worker, triad reads what every attempt ran and leads `report.md` with notices. A model switch that relay's own Claude Code performs inside a worker is detected and reported, not prevented.
- **Environment.** `BRIDGE_MODELS_FILE` (another table), `BRIDGE_MODELS_EVIDENCE` (another evidence file; its promotions ledger sits beside it), `BRIDGE_MODELS_GATE` (`warn`, the default, or `refuse`), `BRIDGE_MODELS_PROMOTE` (`off` stops new automatic promotions), `BRIDGE_CODEX_FIXED_ROOT` (a path prefix for the two default fixed directories of Codex discovery, `/opt/homebrew/bin` and `/usr/local/bin`; the tests point it at an empty directory so no host binary is found), and the check's test and diagnostic hooks `BRIDGE_MODELS_NPM_URL`, `BRIDGE_MODELS_DEPRECATIONS_URL`, `BRIDGE_MODELS_OVERVIEW_URL` (one URL each).

## What you can do

| In Claude Code | In Codex | What happens |
|---|---|---|
| `/codex review [--base ref \| --commit sha] [--focus …] [--intent-stdin] [--allow-large]` | `$claude review` or the `claude_review` tool | The engine freezes the change into `review.patch` (staged, unstaged and untracked work, or the commit range) and every seat reviews that same file independently (defect-first, P0–P3, file:line, fix, confidence). The merger produces one table with attribution and consensus marks and lists every member title so nothing is lost; two findings merge only when their titles agree and, when both propose a fix, the fixes agree too (a lexical test for the same defect); otherwise they stay separate rows linked with a "possibly the same as" note. A merged row's details list every member's explanation and fix, attributed, so nothing is merged silently and nothing is hidden. A seat that returns no usable findings JSON counts as failed. If the change or the rest of the working tree moves during the review (tracked modifications and untracked files by content; ignored files are not watched), the report says so. Changes over 4,000 diff lines are refused unless `--allow-large`. Default seats: `astra:ultra,sol:ultra,opus:max` from Claude Code; `opus:max` from Codex. |
| `/codex ask <question>` | `$claude ask` / `claude_ask` | One hard question, answered with read-only access to the repository. Default `astra:ultra` from Claude Code; `fable:max` from Codex. |
| `/codex council <question>` | `claude_ask` with several seats | The same question to every seat, answers side by side. |
| `/codex fanout --spec spec.json` | `bridge.py fanout` | Many tasks with different prompts, any seats per task, one job, merged findings. This is how to orchestrate several Astra instances on different slices of a problem. |
| `/codex task [--write [--shell]] <task>` | `$claude task` / `claude_task` | Delegate work to one seat. Read-only unless `--write`; a Claude write seat gets a shell only with `--shell`. |
| `/codex reply <job> [--seat …] <msg>` | `claude_reply` | Follow-up inside the seat's own thread or session. Its context, not yours. |
| `/codex status [job]`, `/codex monitor` | `claude_status` / `bridge.py status/monitor` | Per seat: state (`running`, `waiting` on the usage-limit ladder, `done`, `failed`, `cancelled`), elapsed, context (Claude seats: exact tokens and % of the model's window after every call; Codex seats: per-turn totals only, since `codex exec` does not expose occupancy), tokens, turns, steps, last activity; the job's `NOTICE:` lines (a failed or unverified models check, a fallback) under the job line. The job list shows each job's notice count with its first notice and marks a seat that fell back (`requested -> ran`). |
| `/codex result`, `cancel`, `doctor` | `claude_result` / same | Bookkeeping and health. `cancel` is durable: it stops running seats, interrupts a usage-limit wait, and prevents retries. From Codex, `claude_review`/`claude_task` with `wait: false` return the job id at once and the job outlives the call; poll with `claude_status`, collect with `claude_result`. |

Exit status: 0 every seat succeeded · 3 partial (some seats failed; usable output) · 1 every seat failed · 2 usage error.

## What is enforced, and what is only instructed

- **Claude seats** run under Claude Code's restricted profile: an explicit tool list, no MCP servers, no inherited user or project permissions, startup context about 4,400 tokens (versus about 29,000 with a normal profile; the seat's context then grows with what it reads). Read-only seats (`ask`, `review`, `council`) have `Read`, `Grep`, `Glob` and no shell, so they cannot write. Write tasks add edit tools and still no shell; `--shell` adds a fenced Bash tool (git status/diff/log/add and test commands) with direct `git commit` and `git push` denied. That shell is instructed, not filesystem-confined.
- **Codex seats** run in Codex's own sandbox: read-only for `ask`/`review`/`council`, workspace-write (edits confined to the repository) for `task --write`, and the user's Codex MCP servers and plugins are never loaded into a read-only seat; `--with-user-config` loads them for write tasks only. `--full-access` (no sandbox) exists for Codex seats only and must be requested explicitly. The engine uses `CODEX_BIN` when it is set; otherwise it considers every `codex` on PATH, then the ChatGPT app's bundled Codex, `~/.local/bin`, `/opt/homebrew/bin` and `/usr/local/bin`, keeps those that answer `--version` and support `exec --json --output-schema --output-last-message`, and takes the first whose version meets the table's highest Codex floor, else the first capable one.
- **The reverse bridge** (`claude-bridge` MCP server in Codex) auto-approves only the read-only tools. `claude_task` with `write: true` needs both a Codex approval prompt and a server started with `CLAUDE_BRIDGE_ALLOW_WRITE=1`. Arguments are validated against strict schemas before anything runs; prompts travel to the engine on stdin; reads are confined to the server's authorized root (`CLAUDE_BRIDGE_ROOT`, default its start directory), and the engine enforces the same boundary itself through `BRIDGE_ROOT`, so a git top level above the root is never adopted as the working directory; cancelled or timed-out calls have the engine's process group and any seat it recorded killed, with the seat's identity re-checked first.
- **Job files** live under `~/.cache/codex-claude-bridge/jobs/`, directories `0700`, files `0600`; job references are confined to that root. Prompts reach both CLIs on stdin, never on the command line.
- **Timeouts and `cancel`** kill the seat's whole process group and, because Codex runs sandboxed commands in their own sessions, also the commands the seat started (the descendant tree is snapshotted while the seat is alive and each member is re-verified before it is signalled); a hung, silent seat cannot run forever, and a descendant that keeps the output pipe open after the seat's leader exits is killed after a short drain. A process group whose ownership cannot be proven is never signalled. Every failure is a recorded result; a job always reaches a terminal state, even when the engine itself crashes mid-mode, and `result <job>` exits with that outcome (0 done, 3 partial or still running, 1 failed or cancelled).
- **Usage limits**: when a seat hits a Claude or Codex usage limit, the engine makes three attempts twenty seconds apart, then waits an hour and repeats, visibly as the seat state `waiting`, until `cancel` or a `--timeout` ends it. A seat that had already started working is resumed in its own thread or session with a continuation instruction, so completed steps are not repeated; a seat that had not started is simply relaunched. With the `/relay` skill installed and holding accounts for the vendor, seats run on relay-routed accounts instead (`account=<label>` in the footer and `status`) and a limited seat moves to the next account: Codex restarted with its original prompt (a write task that had begun work fails explicitly), Claude continued in its session; `BRIDGE_ROUTER=off` restores the ladder-only behaviour.

## Install

### Friends: the zip (no git, no marketplace)

`bash package.sh` builds `claude-codex-bridge-<version>.zip` (one folder: the skills, engine, MCP server, bootstrap, tests, `INSTALL.md`, a `VERSION` stamp; no audit records). The friend unzips it to `~/claude-codex-bridge`, runs `bash ~/claude-codex-bridge/install.sh`, and restarts Claude Code and Codex. `install.sh` is the bootstrap in standalone mode: it creates the four Claude-side links and the Codex skill link into that folder, registers the MCP server, and writes the PATH shim if needed; `--check` previews, `--uninstall` removes exactly what it installed. `INSTALL.md` is the friend-facing guide.

### Anyone, on any machine (plugin)

```bash
claude plugin marketplace add <owner>/claude-codex-bridge
claude plugin install claude-codex-bridge@claude-codex-bridge
claude plugin list --json     # the installPath field shows where bootstrap.sh lives
<installPath>/bootstrap.sh
```

The bootstrap: checks prerequisites (`python3`, `git`, `file`) and reads the model table's CLI floors before touching anything; chooses a `codex` with the engine's rule (`CODEX_BIN`; else the first candidate meeting the table's Codex floor, else the first capable one) over these candidates, in this order: every `codex` on PATH, a standalone kept at `~/.local/bin`, the executable the wrapper it owns there runs when an earlier run left one (a Homebrew keg path is read as the stable `<prefix>/bin/codex` link when that exists), the ChatGPT app's bundled Codex (first at `Contents/Resources/codex-cli/bin/codex`, where app build 26.928 and later keep it, then at the legacy `Contents/Resources/codex`), then `/opt/homebrew/bin` and `/usr/local/bin`. The engine's order differs: it skips the wrapper on PATH, considers the app's bundled Codex before `~/.local/bin` (where it probes whatever is at `~/.local/bin/codex`, the wrapper included), and never considers the wrapper's target separately. So the two can choose differently, and then the bootstrap reports on, checks sign-in with and registers through one executable while the engine's seats run another: when `~/.local/bin` is off PATH and both the standalone there and the app's Codex meet the floor (the bootstrap keeps the standalone, the engine runs the app's; on PATH, both find the standalone first); whenever an owned wrapper's target and the app's Codex both meet the floor, whatever PATH says (the bootstrap keeps the wrapper's target, the engine runs the app's); when a link on PATH resolves to the app's new launcher and another standalone follows it on PATH (the bootstrap takes the link, which it counts as a standalone; the engine leaves the link to the app launcher's place and takes the standalone); and when no candidate meets the floor and npm is unavailable, or installs one still below it, where each takes its own first capable candidate, so the version the bootstrap reports and the upgrade hint it gives can describe a different executable from the one the engine runs. It installs a current Codex with npm when none meets the floor, and only trusts one that answers `--version` within ten seconds; writes the wrapper script it owns onto PATH to run the chosen executable without ever writing through a symlink or into an application bundle, backing up any unrelated file it finds there; when an app update has moved the bundled Codex and left that wrapper exec'ing a path that no longer exists, a rerun finds the bundled Codex at its new place and re-points the wrapper, without npm; reports both CLI versions against the floors (`Codex version`, `Claude Code version`: `FAILED` with the fix below a floor) and warns by name about an `ANTHROPIC_*_MODEL` override; checks both sign-ins; links the `$claude` skill into `$CODEX_HOME/skills`; registers the `claude-bridge` MCP server in Codex with a locked, atomic, backed-up edit of `config.toml` (one-hour tool timeout, per-tool approval, forwarded account variables); optionally installs OpenAI's official Codex plugin for Claude Code (`--no-plugin` to skip; its commands are `/codex:…` with a colon). `--check` reports and changes nothing. Re-running it after a plugin update refreshes the links and registration it owns. Restart open sessions afterwards.

### Accounts and tokens

- **Default: local sign-ins.** `codex login` (any ChatGPT plan with Codex) and running `claude` once. The bridge never sees credentials; the CLIs do.
- **Headless or shared machines:** `claude setup-token` prints a long-lived token for a subscription; export it as `CLAUDE_CODE_OAUTH_TOKEN` (the engine preserves it for every Claude seat). For Codex use `codex login --device-auth`, or pipe a key into `codex login --with-api-key`. API keys (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) also work if you prefer metered billing. `doctor` shows which is active.
- **Two accounts on one machine:** point `CODEX_HOME` and `CLAUDE_CONFIG_DIR` at separate directories before launching; the bootstrap forwards both into the MCP server and the engine follows whichever is active.

### Kevin's multi-machine layout

This directory lives inside the skills sync repo; the repo's `link.sh` links `skills/codex`, `skills/gpt`, the agents, and `codex-skills/claude` into `~/.claude` and `~/.codex/skills` on every machine at every sync. `bootstrap-multimodel.sh` at the repo root points here. `publish.sh <remote>` pushes this directory to its own public repository (normal push; `--rewrite <expected-remote-oid>` for a deliberate history rewrite; `--dry-run` to see the commands).

## Why it is built this way

- **CLIs, not an MCP server for GPT.** OpenAI deprecated `codex mcp-server`. The engine runs `codex exec` per seat: about 3 seconds of startup, full control of model and effort, JSON findings enforced by Codex's output-schema flag, and persisted threads so follow-ups work. Claude seats run `claude -p` the same way.
- **Context hygiene by construction.** Every seat is a separate process with an empty context; the calling agent only ever receives a bounded, merged result; the raw streams stay on disk. The frozen patch keeps the seats' inputs *identical*; it does not make them small. A seat reads the whole patch and whatever else it chooses to open, so large reviews should be sliced with `fanout` (or reviewed per commit) rather than forced through with `--allow-large`.
- **Codex → Claude goes through MCP** because Codex launches MCP servers outside its command sandbox, which `claude -p` needs (network, home directory). The server is small, dependency-free, and shells out to the same engine.
- **Parallel by default.** Wall-clock time is the slowest seat, not the sum.

## Files

- `skills/codex/` — the `/codex` skill, the engine (`scripts/bridge.py`), the model table (`models.json`: families, current models, floors, refusals, the pinned seat) and its reader, resolver, validator and check (`scripts/bridge_models.py`), the merger (`scripts/merge_findings.py`), the shared findings schema, prompts, tests and stub CLIs.
- `skills/gpt/` — alias. `codex-skills/claude/` — the Codex-side skill (`$claude`), its MCP server, a thin entry point onto the same engine, and its tests. It lives outside `skills/` on purpose: Claude Code discovers plugin skills there, and this one is for Codex only.
- `agents/opus-reviewer.md`, `agents/opus-consultant.md` — optional in-process Claude Code subagents (read-only, no shell).
- `bootstrap.sh` (three modes: repository sync, marketplace, standalone; `--uninstall`), `install.sh` (the zip's entry point), `package.sh` (builds the zip), `publish.sh`, `INSTALL.md`, `tests/test_bootstrap.sh`, `.claude-plugin/` (plugin and marketplace manifests).
- `docs/DECISIONS.md` — the decision log; `docs/audit/` — the 2026-09-06 audits, the synthesis, and the fan-out spec used to run seven Astra auditors at once.
